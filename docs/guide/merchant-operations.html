Merchant Operations ​

OpenWave merchant operations are built around recoverable records. A merchant should be able to prove what happened to a transaction, settlement, checkout channel, or webhook delivery without relying on a single browser session or a lost webhook.

Go-live readiness ​

Before live traffic is enabled, a merchant should have:

AreaExpected state
WebhooksAt least one active endpoint with subscribed event types and a successful test delivery.
ContactOperational email and phone for reconciliation or incident notices.
BrandingDisplay name and customer-visible logo where hosted checkout is used.
SettlementOne approved active settlement account marked as default.
AccessSandbox key tested; live access enabled only by operations policy.
OriginsAllowed browser origins configured for hosted or direct API flows.

Readiness is visible to the merchant, but live enablement is controlled by Astro operations or the implementing OpenWave operator.

For direct-integration merchants, readiness should also confirm which model the merchant is approved for:

  • Hosted Checkout via Merchant API: merchant backend creates the session, customer redirects to OpenWave checkout.
  • Trusted Merchant-Hosted Checkout: customer stays fully inside the merchant website or app after explicit Astro approval.

For Ezone-style onboarding, use Ezone Quick Start as the merchant handoff page.

Settlement accounts ​

OpenWave supports merchants with more than one approved settlement account. This lets a merchant route different checkout channels to different bank accounts while keeping legacy integrations working.

Each account record should expose support-safe fields:

json
{
  "id": 12,
  "label": "Default LYD settlement",
  "bank": {
    "name": "Andalus Bank",
    "handle": "andalus",
    "code": "027"
  },
  "account": {
    "iban_masked": "LY97***************1016",
    "account_number_masked": "****1016"
  },
  "status": "ACTIVE",
  "is_default": true
}

Exactly one active account should be default. Existing merchant API keys and checkout requests without an explicit checkout channel continue to route to the default account for backward compatibility.

Merchants can view approved accounts and choose the default among active accounts. They should not directly edit bank account details. New accounts, account changes, and suspensions should go through an account request workflow reviewed by operations.

Account request history should be recoverable from the portal and API:

http
GET /api/v1/merchant/settlement/account-requests?status=PENDING_REVIEW&request_type=NEW_ACCOUNT

Supported request types are NEW_ACCOUNT, CHANGE_ACCOUNT, and SUSPEND_ACCOUNT. Supported review states are PENDING_REVIEW, APPROVED, REJECTED, and CANCELLED. Responses should be merchant-scoped, paginated, and capped to 100 rows for JSON. They should expose masked account details and review notes, not raw account numbers beyond what the merchant submitted in a new request body.

Merchant account request exports should use the same filters with format=csv, start from the first page, and apply a bounded export cap. CSV rows should include request id, type, status, target/result account ids, label, bank handle/name/code, masked IBAN, masked account number, reason, review note, reviewer, review timestamp, and created/updated timestamps. They must not include raw full IBANs, raw account numbers, API keys, checkout channel keys, webhook signing secrets, private keys, or raw request payload bodies.

For operator portals, account request queues should also support bounded status/type filters and support-safe search over merchant name, request id, bank handle/name, label, and reason. Search should not require scanning raw IBAN or account-number fields.

Checkout channels ​

Checkout channels are merchant-controlled routing surfaces. A channel has its own purchase key and points to one approved active settlement account.

Common uses:

  • separate ecommerce, POS, invoice, and subscription traffic
  • route a checkout product line to a specific bank account
  • rotate one purchase key without disturbing other channels
  • filter reports and webhook logs by account or channel

Channel keys are sensitive. They should be revealed only once on create or rotation, and reports should show channel IDs or labels, not raw keys.

Creating a channel returns the scoped purchase key once:

http
POST /api/v1/merchant/checkout/channels
Authorization: Bearer <merchant_key>
Content-Type: application/json
json
{
  "name": "Mobile app checkout",
  "merchant_account_id": 15,
  "environment": "LIVE"
}
json
{
  "channel": {
    "id": 4,
    "merchant_account_id": 15,
    "name": "Mobile app checkout",
    "environment": "LIVE",
    "status": "ACTIVE",
    "has_key": true
  },
  "api_key": "mk_live_example_not_a_real_key",
  "masked_key": "mk_live_...abcd",
  "warning": "Copy this key now - it will not be shown again."
}

The raw api_key is not retrievable later. If it is lost, rotate the channel key and update the checkout integration using that channel.

Merchants may rename a channel or move future traffic to another approved active settlement account:

http
PATCH /api/v1/merchant/checkout/channels/{channel_id}
json
{
  "name": "Mobile app checkout",
  "merchant_account_id": 15
}

The channel id, environment, status, and existing purchase key remain unchanged. Historical payments, webhook deliveries, and settlement reports keep the original merchant_account_id and checkout_channel_id values so reconciliation does not change after a route edit. Rerouting to suspended, archived, or unapproved accounts should be rejected.

Direct-integration merchants can use checkout channels to separate sandbox and live traffic or to split ecommerce, app, invoice, and subscription routes without maintaining multiple unrelated merchant accounts.

Reports ​

Merchant report APIs should be paginated, bounded, and scoped to the authenticated merchant.

ReportImportant filtersRecovery fields
Transactionsstatus, environment, merchant_account_id, checkout_channel_id, from, tosession id, merchant reference, OpenWave reference, amount, currency, status, bank handles, settlement account label/bank/masked IBAN, checkout channel label/environment
Settlementsstatus, merchant_account_id, checkout_channel_id, settlement date from, settlement date tobatch id, item id, gross, fees, bank cut, net, settlement date, settlement account label/bank/masked IBAN, checkout channel label/environment
Webhooksevent_type, status, webhook_endpoint_id, merchant_account_id, checkout_channel_id, from, toevent id, delivery id, endpoint id, attempts, response status, retry timestamps, settlement account label/bank/masked IBAN, checkout channel label/environment

JSON responses should cap limit to 100 rows. CSV exports are optional but recommended; when implemented, they should page or cap internally and avoid unbounded memory loads.

CSV exports for transaction, settlement, and webhook reports should include the same support-safe route context exposed by JSON rows: merchant_account_label, merchant_account_bank_handle, merchant_account_bank_name, merchant_account_iban_masked, checkout_channel_name, and checkout_channel_environment. This lets merchants reconcile multi-account and multi-channel routing without exposing raw credentials or full account details.

Reports must not export raw API keys, webhook signing secrets, OAuth tokens, full IBANs, raw account numbers, national IDs, or raw webhook request bodies. Payload recovery can be provided from an authenticated detail view with sensitive fields masked.

Webhook recovery ​

Webhook delivery is not the only source of truth. Merchants should be able to recover missed events from the portal or API.

Managed webhook endpoints should be configured through the Merchant Portal or the merchant-scoped endpoint API:

http
GET /api/v1/merchant/webhook-endpoints
POST /api/v1/merchant/webhook-endpoints
PUT /api/v1/merchant/webhook-endpoints/{endpoint_id}
POST /api/v1/merchant/webhook-endpoints/{endpoint_id}/rotate-secret
POST /api/v1/merchant/webhook-endpoints/{endpoint_id}/test

Implementations may keep /api/v1/webhooks/endpoints as a backward-compatible alias for earlier integrations, but new merchant-facing docs and portal examples should use the merchant-scoped path.

Recommended delivery log fields:

json
{
  "event_id": "evt_01J...",
  "delivery_id": "whd_01J...",
  "event_type": "payment.completed",
  "status": "FAILED",
  "webhook_endpoint_id": 7,
  "merchant_account_id": 12,
  "checkout_channel_id": 4,
  "payment_session_id": "ops_01J...",
  "attempt_count": 3,
  "last_response_status": 500,
  "next_retry_at": "2026-06-04T11:30:00Z",
  "created_at": "2026-06-04T10:45:00Z"
}

Merchants should be able to:

  • add, update, disable, and test webhook endpoints
  • subscribe endpoints to specific event types
  • rotate endpoint signing secrets with one-time reveal
  • filter delivery logs by event, endpoint, route, status, and date
  • copy or recover masked payload details for events they own

Operators should also expose a bounded webhook health summary for portal and direct API users. In Neptune Astro this is available at GET /api/v1/webhooks/health for the authenticated merchant. The response includes total deliveries, delivered/failed/pending/processing counts, recoverable counts, active/disabled endpoint counts, event type grouping, per-endpoint delivery stats, and recent failed delivery metadata. It does not include raw signing secrets or unmasked payload bodies.

For Ezone-style onboarding, operator guidance should explicitly say that webhook management is supported in the portal and by API, and that direct integration does not require an external SDK or merchant-built bank-auth page.

Bank-origin merchant events ​

Some events start at a bank adapter, for example an account-status or CBS-reference update for a merchant settlement account. OpenWave should standardize the merchant-facing event names and payload fields, but the bank adapter implementation remains bank-specific.

The standard path is:

text
Bank adapter -> OpenWave operator -> Merchant webhook endpoint

For Neptune and Andalus, Nexus can be one implementation of the bank adapter path. Nexus is not a required OpenWave component, and other banks can implement their own adapter as long as the merchant-facing OpenWave event contract is preserved.
