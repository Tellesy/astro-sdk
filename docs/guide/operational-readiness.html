Operational Readiness ​

OpenWave operators should expose readiness and recovery surfaces for merchants, banks, and support teams. These surfaces are operational controls, not payment authorization steps.

Merchant readiness ​

Merchant readiness should include:

  • one approved active default settlement account
  • at least one active webhook endpoint with a successful test
  • sandbox key tested before live enablement
  • live access enabled only by operator policy
  • allowed origins configured for browser integrations
  • operational contact and customer-visible branding
  • direct API enablement state clearly visible when the merchant is approved to integrate without an SDK

Merchants can view readiness and request account changes. Real settlement account activation, suspension, and archived-state changes remain operator-controlled.

When a merchant uses direct integration, readiness should distinguish at least these states:

  • sandbox enabled
  • live pending review
  • live enabled
  • direct API approved
  • webhook test passed

Bank callback readiness ​

Bank callback health is bank-adapter specific. OpenWave defines the operator-facing behavior and merchant event contract; it does not require Nexus or any other single adapter implementation.

Recommended callback health fields:

json
{
  "configured": true,
  "status": "OBSERVED",
  "total_events": 128,
  "delivered": 124,
  "failed": 4,
  "ready_tests": 2,
  "path_health": [
    {
      "callback_path": "/execute-transaction",
      "status": "ATTENTION_REQUIRED",
      "total_events": 12,
      "delivered": 8,
      "failed": 4
    }
  ]
}

Neptune Astro exposes bank-scoped callback readiness through /api/v1/bank/webhook-endpoints/health and callback event recovery through /api/v1/bank/webhook-endpoints/events. Banks can update their controlled callback URL through /api/v1/bank/webhook-endpoints/default and record a readiness test through /api/v1/bank/webhook-endpoints/test. The older /api/v1/bank/self/* paths remain compatibility aliases. The callback center keeps sensitive keys, settlement routing, and internal adapter credentials under operator control.

Bank callback event exports should include support-safe recovery fields such as callback path, callback group, target host, sanitized target URL, status, recoverable flag, response status, message, and created timestamp. Sanitized target URLs should omit query strings, fragments, user info, raw callback keys, and other receiver-side secrets.

Incident readiness ​

Incident queues should be derived from existing records instead of a separate workflow engine for v1. Typical incident sources include failed merchant webhooks, failed bank callbacks, reconciliation-required payments, expired customer-active sessions, and settlement failures.

Dashboard and report endpoints should return partial warnings when one dependency fails. First-load portal pages should not fail because one count or section cannot be calculated.

Operator reports ​

Operator and support portals should expose bounded payment, webhook, settlement, and merchant-readiness reports. These reports are implementation-specific surfaces, but compliant OpenWave operators should keep the recovery fields consistent with merchant-facing reports so support can reconcile a case without asking the merchant for screenshots or raw payloads.

Recommended operator report filters:

ReportFilters
Paymentsmerchant_id, bank_handle, status, environment, merchant_account_id, checkout_channel_id, date range, support-safe search
Webhooksmerchant_id, status, event_type, webhook_endpoint_id, merchant_account_id, checkout_channel_id, date range, support-safe search
Settlementsbank_handle, status, settlement date range
Settlement itemsmerchant_id, bank_handle, status, merchant_account_id, checkout_channel_id, settlement date range, support-safe search
Merchant readinessmerchant_id, bank_handle, readiness status, environment, support-safe search

Settlement batch reports are bank/date/status summaries. Settlement item reports are the operator drill-down for merchant reconciliation and should expose payment session, refund, recurring-charge, gross, fee, bank-cut, net, and route context fields.

JSON and CSV report rows for payments, webhooks, and settlement items should include support-safe route context when available:

  • merchant_account_label
  • merchant_account_bank_handle
  • merchant_account_bank_name
  • merchant_account_iban_masked
  • checkout_channel_name
  • checkout_channel_environment

This context is important for multi-account merchants because historical payments and webhook deliveries must remain tied to the account and checkout channel used at the time of the event, even if the merchant later changes their default account or reroutes a channel.

Operator CSV exports should use the same safe route context as JSON rows. They must not include full IBANs, raw account numbers, API keys, checkout channel keys, webhook signing secrets, OAuth tokens, private keys, national IDs, raw customer identifiers, or raw webhook payload bodies.

Support-safe admin data ​

Admin and bank-support portals often need customer and user lookup to resolve payment, alias, mandate, and webhook incidents. Those views should be useful for recovery without becoming a secondary source of sensitive identifiers.

Recommended behavior:

  • search and ownership checks may match stored identifiers server-side
  • list/detail responses should return masked phone numbers, national IDs, and portal emails
  • copied support summaries should use masked values only
  • user-operation CSV exports should include role, status, bank id, 2FA state, and timestamps, not password hashes or reset tokens
  • alias/customer CSV exports should include support-safe customer references, masked contact identifiers, bank handle, status, and masked linked accounts
  • bank registered-customer reports should be bank-scoped, paginated at the Identity source where possible, filter-aware, and limited to alias, status, masked phone, enrollment, account-count, and masked default-route fields
  • bank customer consent/mandate CSV exports should be bank-scoped, filter-aware, bounded, and limited to support-safe consent, mandate, merchant, settlement-route, and checkout-channel references

Compatibility keys can remain stable for older portal code, but their values should be masked once they are returned to an operator UI. Implementations may also expose explicit fields such as customer_phone_masked, national_id_masked, and portal_email_masked so new clients do not mistake masked compatibility fields for raw data.

In Neptune Astro, bank registered-customer reporting is exposed at GET /api/v1/bank/reports/customers with search, active-only filtering, pagination, and bounded CSV export. Astro requests a bounded page from OpenWave Identity rather than fetching every linked identity. OpenWave Identity keeps GET /identity/accounts backward compatible while accepting optional page, limit, and search parameters for bank-key authenticated callers.

Bank settlement operations should expose both batch summaries and bank-scoped item reconciliation. In Neptune Astro, GET /api/v1/bank/reports/settlements returns batch-level totals for the authenticated bank, while GET /api/v1/bank/reports/settlement-items returns item-level payment, refund, and recurring-charge rows scoped to that same bank. Item exports support merchant, settlement route, channel, date, status, and support-safe search filters, and include masked settlement account context only.

Recovery rules ​

  • Keep report and recovery endpoints paginated.
  • Cap JSON limits to a small maximum, normally 100 rows.
  • CSV exports should page internally or enforce a safe cap.
  • Do not export raw API keys, signing secrets, OAuth tokens, national IDs, private account data, or unmasked webhook payload bodies.
  • Keep bank adapter failures observable without making one bank's adapter a mandatory OpenWave component.
